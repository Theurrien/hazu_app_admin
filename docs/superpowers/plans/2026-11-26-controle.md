# Bulk Import → Contrôle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new Bulk Import workflow « Contrôle » that links every file value (student, class, company, canton) to Hazu with saved correspondences, checks each student row against its rooms, and fixes selected lines through the Task Queue.

**Architecture:** Two pure cores in `src/shared/` (resolution of file values → Hazu with saved links; the per-pair cross-check and fix list), a small local-SQLite table behind three IPC channels, and a three-step renderer tab under `components/bulk-import/controle/`. Writes reuse the existing `roleUpdate` task → S4.

**Tech Stack:** Electron, React, TypeScript, Tailwind v4, better-sqlite3, vitest.

**Spec:** [docs/specs/2026-11-26-controle-design.md](../../specs/2026-11-26-controle-design.md) — read it before any task; this plan does not repeat its UI copy or rules where a task can point at it.

## Global Constraints

- Branch `feat/controle` off `main`. One commit per task, message prefix `feat(controle):` / `docs(controle):`, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **No real person data in tracked files.** Tests use invented names and `@example.invalid` addresses. Run `python3 scripts/check-no-person-data.py --all` before the last commit.
- Never start the app against the real userData (`~/Library/Application Support/hazu-admin`). Manual runs: copy it to the scratchpad and start Electron with `--user-data-dir` on the copy.
- Complete mode only: `'controle'` in `ALL_WORKFLOWS`, not in `CIE_WORKFLOWS` ([app-mode.ts](../../../src/shared/app-mode.ts)).
- The renderer imports types/logic from `src/shared/`, never from `src/main/services/`.
- Room types: class column ↔ `rooms.room_type = 'class'`, company ↔ `'enterprise'`, canton ↔ `'state'`. CIE (`'cie'`) is never a candidate and never checked.
- Only the `student` role is checked and fixed. Add = `oldRole '_' → newRole 'student'`; remove = `'student' → '_'`.
- Nothing is ticked by default. No « tick all removals » shortcut.
- Run tests with `npx vitest run <file>`; typecheck main with `npx tsc -p tsconfig.main.json --noEmit` and renderer with `npx tsc -p tsconfig.json --noEmit`.

## Review Focus

1. **Cell spelling noise** — `" Cui 2a "` and `"CUI 2A"` in the same column must be one value with one decision (`roomKey`), while accents stay significant for exact title matching. Test in Task 1.
2. **The same student on two file rows** — checked once, excess computed against the union of both rows' rooms, flagged « deux lignes du fichier ». Test in Task 2.
3. **A saved link to a room or student that has since been archived/removed locally** — « lien périmé », unresolved, never used and never treated as ignored. Tests in Task 1.
4. **A student with two companies in Hazu and the file naming one of them** — one OK line, one « En trop » line carrying `multipleInHazu: 2`; with the file cell empty, no line at all. Tests in Task 2.
5. **The file is replaced while fix tasks are still queued** — the tab resets (mappings, results, ticks) but keeps saved correspondences; a reload that finishes for the old file is discarded. Test of the reset helper in Task 4; generation guard in Task 6.

```ts
export type CorrCategory = 'student' | 'class' | 'enterprise' | 'state';
export type RoomCategory = Exclude<CorrCategory, 'student'>;
export interface SavedLink { category: CorrCategory; fileKey: string; fileLabel: string; hazuId: string | null; decidedAt: number }
export interface RoomCandidate { id: string; title: string; parentTitle: string | null }
export function roomKey(value: string): string;                 // trim, collapse spaces, lowercase
export function studentKeys(p: SheetPerson): string[];          // ['email:x@…'] then ['name:<nameKey>'], only those that exist
export type RoomResolution =
  | { kind: 'saved'; hazuId: string } | { kind: 'exact'; hazuId: string } | { kind: 'ignored' }
  | { kind: 'stale'; suggestionId: string | null } | { kind: 'open'; suggestionId: string | null; twins: string[] };
export function resolveRoomValues(
  category: RoomCategory, values: string[], rooms: RoomCandidate[], saved: SavedLink[],
  suggest: (value: string, titles: string[]) => string | null,   // injected: fuzzyMatch.findBestMatch (normal) lives in the renderer
): Map<string, RoomResolution>;                                   // keyed by roomKey(value)
export type StudentResolution =
  | { kind: 'saved'; personId: string } | { kind: 'matched'; personId: string } | { kind: 'ignored' }
  | { kind: 'stale' } | { kind: 'check'; candidateIds: string[]; reason: 'conflict' | 'ambiguous' | 'near' } | { kind: 'unknown' };
export function resolveStudents(rows: SheetPerson[], students: HazuPerson[], saved: SavedLink[]):
  Map<number, { res: StudentResolution; saveKey: string | null }>; // keyed by rowIndex
export function isResolved(r: RoomResolution | StudentResolution): boolean; // saved | exact | matched | ignored
export function resolvedId(r: RoomResolution | StudentResolution): string | null; // the Hazu id, null for ignored/unresolved
```

Rules (from the spec, « Correspondences » and « Calls settled »):
- Room: saved link first (hazuId null → `ignored`; hazuId not among `rooms` → `stale` with a suggestion); else exact = case-insensitive trimmed equality with **exactly one** title of `rooms` (rooms are already of the category's type) → `exact`; two or more equal titles → `open` with `twins` = their ids and no suggestion; else `open` with `suggest(...)` mapped back to an id.
- Student: if two or more rows share a `name:` key and have no e-mail, that key gets `saveKey: null` and saved `name:` links are not applied to them. Saved lookup tries `studentKeys` in order. A saved person not in `students` → `stale`. A saved person contradicted by the row's e-mail matching **another** student exactly (case-insensitive on `HazuPerson.email`) → `check`, `reason: 'conflict'`, `candidateIds: [saved, emailHit]`. No saved link → the `matchRows` result mapped one to one. `saveKey` = first of `studentKeys` (subject to the collision rule).

- [ ] **Step 1: Write the failing tests** — `correspondence.test.ts`, at least:
  - `roomKey(' Cui  2a ') === roomKey('CUI 2A')`; `roomKey('Écully') !== roomKey('Ecully')`.
  - `studentKeys({rowIndex:0,email:'A.B@Example.invalid',firstName:'Ana',lastName:'Bé'})` → `['email:a.b@example.invalid','name:<nameKey("Ana Bé")>']`; no e-mail → only the name key.
  - saved room link wins over an exact title; saved `hazuId:null` → `ignored`; saved id missing from rooms → `stale`.
  - exact match on one title → `exact`; two rooms titled `CUI 2A` → `open` with both ids in `twins` and `suggestionId: null`.
  - no match → `open` with the id of the title `suggest` returned.
  - saved student link → `saved`; saved person no longer a student → `stale` (not `ignored`).
  - saved link to P1 while the row's e-mail hits P2 exactly → `check`/`conflict` with `[P1,P2]`.
  - two rows `Ana Bé` without e-mail and a saved `name:` link → both fall back to the matcher (`ambiguous` or `unknown`), both `saveKey: null`.
  - `isResolved` true for saved/exact/matched/ignored, false for stale/open/check/unknown.

```ts
export type PairStatus = 'ok' | 'missing' | 'extra' | 'unverifiable' | 'other-role';
export interface PairLine {
  key: string;                    // `${personId}|${category}|${roomId ?? 'file:' + fileValue}`
  personId: string; rowIndexes: number[]; category: RoomCategory;
  fileValue: string | null;       // null on 'extra' lines
  roomId: string | null;          // null on 'unverifiable'
  status: PairStatus;
  hazuRole?: string;              // on 'other-role'
  multipleInHazu?: number;        // enterprise/state only, on 'extra' lines, when the student holds >1 room of that type
}
export interface CheckRow { rowIndex: number; personId: string; cells: Partial<Record<RoomCategory, string>> } // only mapped, non-empty cells
export type CellResolution = { kind: 'room'; roomId: string } | { kind: 'ignored' };
export interface CheckInput {
  rows: CheckRow[];
  mapped: RoomCategory[];                                        // categories whose column is mapped
  cellOf: (category: RoomCategory, value: string) => CellResolution; // every value is resolved before the check runs
  roomCategory: Map<string, RoomCategory>;                       // local rooms of the three types → category
  assignments: Array<{ person_id: string; room_id: string; role: string }>;
}
export interface CheckResult {
  lines: PairLine[];              // every status, OK included; sorted by personId then category
  counts: { students: number; ok: number; missing: number; extra: number; unverifiable: number; otherRole: number };
  duplicatePersons: string[];     // personIds on 2+ rows
}
export function crossCheck(input: CheckInput): CheckResult;
export interface Fix { lineKey: string; personId: string; roomId: string; oldRole: '_' | 'student'; newRole: 'student' | '_' }
export function fixesFor(lines: PairLine[]): Fix[];              // missing → add, extra → remove; any other status → no fix
```

Rules: rows of one person are merged (union of cells per category). Per mapped category with at least one value: each `ignored` value → one `unverifiable` line and **no** `extra` lines for that category; each room value → `ok` (role student in it), `other-role` (assigned with another role), or `missing`; then every room of that category where the person holds `student` and that no value named → `extra`. A category with no value for the person → no lines.

  - canton value ignored → one `unverifiable`, no `extra` even though the student holds a canton.
  - same person on rows 3 and 7 (class A on one, B on the other, holds A and B) → two `ok`, no `extra`, `rowIndexes` hold both, `duplicatePersons` = [that id].
  - a `cie` assignment is never a line (not in `roomCategory`).
  - `fixesFor`: missing → `{oldRole:'_',newRole:'student'}`, extra → `{oldRole:'student',newRole:'_'}`, ok/other-role/unverifiable → nothing.
  - `counts` match the lines.
